## Expanded coverage (this run): serialization, exportData, Tag constructors

Probed corners of the public scope the baseline only lightly touched. Two new findings; the rest clean.

**🟠 S1 — `SensorTag` `toStruct`→`fromStruct` silently produces a data-less tag.**
*Where:* `SensorTag.toStruct` / `SensorTag.fromStruct` (`libs/SensorThreshold/SensorTag.m`).
*Measured:* round-trip of a 2000-point tag → `getXY()` returns **0 points, no error/warning**. `toStruct`
intentionally omits X/Y (documented in *its* help), but `help SensorTag/fromStruct` is a single line
("Reconstruct SensorTag from a toStruct output.") and never says the reloaded tag has no data and that
data must be re-attached (`load`/MatFile/DataStore). Cross-session dashboards built from registered tags
therefore lose their series silently.
*Why it matters:* "save → load" is the natural persistence mental model; a silent empty reload is a trap.
*Fix:* **additive** — warn when a reconstructed tag is queried with no data, and document the
re-attach step prominently in `fromStruct`/`loadFromStructs` help.

**🟠 S2 — `DerivedTag` accepts a wrong-arity `ComputeFn`, then throws raw `MATLAB:minrhs` at `getXY`.**
*Where:* `DerivedTag` constructor / recompute (`libs/SensorThreshold/DerivedTag.m`).
*Measured:* `DerivedTag('sum',{a,b},@(x,Y) Y{1}+Y{2})` (a plausible wrong guess) constructs fine — the
`DerivedTag:invalidCompute` guard only checks *is-a-function-handle*, not arity — then fails at `getXY`
with raw `MATLAB:minrhs :: Not enough input arguments`, **not** the advertised namespaced error. The
correct contract (`@(parents)->[X,Y]`, e.g. `@(p) deal(p{1}.X, p{1}.Y+p{2}.Y)`) *is* documented, so this
is a wrong-guess→raw-error trap, same class as B3 (`MonitorTag` arity).
*Fix:* **additive** — validate `nargin(ComputeFn)` (and output shape) at construction → reuse
`DerivedTag:invalidCompute` with a message stating the `@(parents)->[X,Y]` contract.

**Confirmed clean (positive coverage):**
- ✅ `exportData` — CSV (113 KB) and MAT (52 KB) both written correctly.
- ✅ `StateTag` — numeric **and** cellstr `Y` both construct and `valueAt` correctly (45→`1` / `'run'`).
- ✅ `DashboardEngine.save`→`DashboardEngine.load` — JSON round-trips, reloads, and renders (in-session).
- ✅ `CompositeTag` — `AggregateMode 'and'|'or'|'majority'|…` and `CompositeTag:invalidAggregateMode`

## Expanded coverage round 2: theme/export errors, annotation methods, lifecycle

small new findings.

**🟠 V1 — `DashboardEngine` Theme name not validated at construction (inconsistent with `FastSense`).**
*Measured:* `FastSense('Theme','sunburst_neon')` → gold `FastSenseTheme:unknownPreset` ("Use 'light' or
'dark'."), but `DashboardEngine('x','Theme','bogus')` **constructs with no error**. A dashboard theme typo
gets no feedback at the point of the mistake.
*Fix:* **additive** — validate the dashboard Theme name eagerly, reusing `FastSenseTheme:unknownPreset`.

**🟠 V2 — `addFill(x,y,0)` (Baseline passed positionally) → raw `MATLAB:badsubscript`.**
*Where:* `FastSense.addFill`. Real signature is `addFill(x, y, 'Baseline', val)` — Baseline is a
name-value pair. Passing it positionally (a very natural guess, fails identically before and after render)
throws raw `Index exceeds the number of array elements`. **Same root-cause family as B1** (`FastSense(x,y)`):
a numeric in a name-value *key* slot yields a cryptic raw error instead of the gold `unknownOption`.
*Fix:* **additive** — detect a numeric 3rd positional and accept it as Baseline (or throw a helpful error).

**🟢 P5 — widget `DashboardWidget:unknownOption` list is gold but noisy.** ✅ RESOLVED 2026-06-29 — internal `h*` graphics-handle properties are filtered out of the suggested-options list.
*Measured:* `addWidget('number',...,'Value',1)` → `DashboardWidget:unknownOption` correctly lists valid
options, but the list mixes in internal handle/state props (`hPanel`, `Dirty`, `Realized`, `hCellPanel`,
`hValueText`…) alongside real options (`StaticValue`, `ValueFcn`, `Units`, `Format`…), burying the
user-facing ones. *Fix:* **additive** — filter the suggested list to user-facing options.

## Deferred (not a safe additive fix)

**P4 — repeated install boilerplate in 77/91 examples** (`projectRoot = fileparts(... mfilename ...);
run(install.m)`): **deferred, by design.** This is the path **bootstrap** — it's what puts the libraries
on the path, so it cannot be replaced by a helper call (the helper wouldn't be on the path yet —
chicken-and-egg). Removing it would require a different distribution mechanism (a MATLAB Project `.prj`
or packaged toolbox that auto-sets the path), which is an architectural change outside additive
`/api-polish` scope. Rewriting 77 user-facing reference scripts for a 2-line cosmetic reduction is
high-churn / low-value. Recommendation only.

**Residual P1** — internal process codes still appear in some other Tag headers (`TagRegistry`
"Pitfall 7/8", `StateTag` "legacy StateChannel", a few `DerivedTag`/`CompositeTag` codes). Low user
impact; the flagged worst case (`MonitorTag`) and the specific items (P2 FastPlot, P3 Plan 02) are done.
A dedicated docs pass can mop up the rest.
